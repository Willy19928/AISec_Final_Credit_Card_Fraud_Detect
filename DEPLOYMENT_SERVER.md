# Deployment Server Integration

## Repository Relationship

The model-training and evidence repository is:

- [Willy19928/AISec_Final_Credit_Card_Fraud_Detect](https://github.com/Willy19928/AISec_Final_Credit_Card_Fraud_Detect)

The reference inference and Azure deployment repository is:

- [Willy19928/Credit_Card_Fraud_Detection_Server](https://github.com/Willy19928/Credit_Card_Fraud_Detection_Server)

The deployment server was forked from
[joe50304/azure_cloud_inference](https://github.com/joe50304/azure_cloud_inference)
and modified from a MobileNet image-classification service into a credit-card
fraud transaction scoring service.

This repository remains the source of truth for training, evaluation metrics,
security tests, cards, and generated model artifacts. The deployment repository
is the serving implementation.

## Research Reference

The deployment controls are documented with reference to Zhang et al.'s
SecMLOps framework:
["SecMLOps: A comprehensive framework for integrating security throughout the
machine learning operations lifecycle"](https://doi.org/10.1007/s10664-025-10795-y).
In particular, the deployment repository implements artifact provenance and
integrity checks, strict transaction input validation, controlled offline model
replacement, CI validation, and model-version reporting. These controls align
with the paper's recommendations for provenance tracking, automated security
checks, input validation, checksums, and controlled deployment.

The paper is used as a reference for explaining these controls, not as the
source design for the server. The classroom server does not implement the
paper's full production monitoring, authentication, authorization,
incident-response, or organizational-governance model. See
`RESEARCH_REFERENCE.md` for the complete project-to-paper mapping.

## Artifact Flow

Running the notebook generates the artifacts required by the server:

| Training repository artifact | Deployment repository destination | Purpose |
| --- | --- | --- |
| `artifacts/models/primary_mlp.pt` | `models/primary_mlp.pt` | MLP state dictionary, feature order, architecture, and decision threshold |
| `artifacts/models/preprocessing.joblib` | `models/preprocessing.joblib` | Training-fitted scalers and final feature-column order |
| `artifacts/run_metadata.json` | `models/run_metadata.json` | Training run, dataset checksum, artifact set ID, and evaluation-limit metadata |
| generated by `scripts/update_model_manifest.py` | `models/model_manifest.json` | Startup SHA-256 checks for the deployed artifacts |

The checkpoint, preprocessing artifact, and run metadata must come from the same
notebook run. Deploying a new model without its matching artifacts can cause
training-serving skew or publish incorrect provenance.
After copying them, run the server repository's manifest script before startup
so `VERIFY_MODEL_HASHES=1` accepts the new files.

## Serving Input Contract

The inference API accepts exactly 30 raw numeric transaction fields:

```text
Time, V1, V2, ... V28, Amount
```

The server uses `preprocessing.joblib` to reproduce the notebook's runtime
features:

```text
V1 ... V28, Hour, Hour_sin, Hour_cos,
scaled_Time, scaled_Amount, scaled_log_Amount
```

The API rejects missing fields, unknown fields, JSON strings, JSON booleans,
non-numeric values, non-finite values, values outside the supported inference
range, negative `Time`, and negative `Amount`.

## Decision Policy

- Model architecture: `FraudMLP(96-48-16)`
- Packaged decision threshold: `0.9838983416557312`
- Score below threshold: normal flow
- Score at or above threshold: human review

The deployment server does not automatically block accounts or punish
customers.

## Server Capabilities

- Browser-based single-transaction review console.
- Normal and fraud example transactions.
- Example transactions are public dataset examples for UI demonstration, not
  independent evaluation evidence.
- JSON batch inference.
- Offline model and preprocessing artifact replacement before service startup.
- Checkpoint and preprocessing validation before startup serving.
- Flask API served through Gunicorn.
- Docker and Azure VM deployment instructions.

Replacement artifacts must:

- contain a `FraudMLP(96-48-16)` state dictionary;
- include the matching `preprocessing.joblib` from the same notebook run;
- include the matching `run_metadata.json` from the same notebook run;
- use the same 34 model features and feature order;
- include a finite threshold between `0` and `1`;
- contain only finite model parameters;
- have fitted scaler artifacts that pass a probe transform;
- have a regenerated `models/model_manifest.json` with matching SHA-256 values
  and a deployment artifact set ID.

The deployment server intentionally does not accept live model or joblib uploads.
Model updates are made by replacing local artifacts before startup and
restarting the service.

## Replace Artifacts Before Startup

After rerunning the notebook, update the deployment server from inside the
server repository:

```powershell
$TrainingRepo = "C:\path\to\AISec_Final_Credit_Card_Fraud_Detect"
Copy-Item "$TrainingRepo\artifacts\models\primary_mlp.pt" .\models\primary_mlp.pt -Force
Copy-Item "$TrainingRepo\artifacts\models\preprocessing.joblib" .\models\preprocessing.joblib -Force
Copy-Item "$TrainingRepo\artifacts\run_metadata.json" .\models\run_metadata.json -Force
python .\scripts\update_model_manifest.py
docker compose restart
```

If the container has not been created yet, use `docker compose up -d --build`
instead of `docker compose restart`.

## Start The Server

```bash
git clone https://github.com/Willy19928/Credit_Card_Fraud_Detection_Server.git
cd Credit_Card_Fraud_Detection_Server
docker compose up -d --build
```

Open `http://localhost`.

For Azure VM deployment, security configuration, environment variables, and
complete API examples, follow the deployment repository's README.

## Deployment Security Boundary

The reference server is suitable for classroom demonstration and controlled
testing. A production deployment still requires:

- authentication and authorization;
- TLS termination;
- rate limiting and request-size enforcement;
- audit logging and monitoring;
- input, score, and review-workload drift monitoring;
- rollback and incident-response procedures;
- protection of transaction data and model artifacts.
